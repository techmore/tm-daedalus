## Admin workflow

Use **Add or join workspace → Add a customer**. Platform administrators see **Onboarding — complimentary access for 30 days, without DNS changes** and a reason field. Each new domain gets an independent workspace, the normal domain verification challenge, daily public checks and a dated 30-day onboarding approval. DNS ownership remains pending; no DNS records are changed by this workflow.

The same dialog includes **Customer onboarding**, listing existing customer workspaces administered by the signed-in platform administrator. **Approve onboarding for 30 days** starts a transition for an existing customer, **Reapprove for 30 days** renews an expired approval, and **End onboarding** ends that exception. Every decision requires a reason and records the actor, version and deadline in the workspace audit log.

At the deadline, the platform admin dashboard shows the number of customer approvals that need review, across their approved customer workspaces and regardless of the selected topic. **Review customer access** opens the review dialog explicitly. Each customer can be reapproved or ended separately. **Close review** or Escape closes the dialog. Initial load, page refresh, minute polls and newly due customers update the reminder without opening a dialog or moving focus. The reminder disappears when no customers need review. A failed refresh retains the last loaded count with an unavailable-refresh label. The page checks once per minute while visible; reopening the customer dialog also refreshes the list. Due records remain available on the next visit, and the scheduler creates a durable workspace notification once per approval version.

Background refreshes preserve a focused decision form and its observed version. Unchanged lists preserve unsaved reasons even when focus has moved elsewhere. A stale submitted version still receives the normal conflict response; the UI retains the reason and displays that response. Successful decisions wait for a fresh count and list after any already-running background request, so an older response cannot leave the pre-save version behind. If the decision succeeds but the list refresh fails, the UI says the decision was saved and offers **Refresh customer access**. That action retries the list request without repeating the decision; stale decision controls stay disabled until a fresh list is available. Closing a review returns focus to the reminder action, or to the visible customer action when the reminder has cleared.

An expired or ended onboarding grant stops providing the DNS exception. For an otherwise unverified workspace, scanner enrollment, scan commands, active website assessment and member sharing controls close. Queued scans are cancelled and active scans receive the existing cancellation request. Saved reports, established memberships and ordinary public DNS/website checks remain available. A separately verified domain or another valid pre-existing override continues to supply its own authorization. Renewing a customer does not resume cancelled scans automatically.

## Workspace access and ownership instructions

Each **Overview → Workspace access** section groups domain ownership, current control availability, the user's role and approval deadlines. Topic assessments appear first. Workspace members can read the status; workspace admins can open the TXT instructions and manage temporary 14-day approval. Live refreshes update these facts and restore scanner and website controls after approval, while an action already in progress remains disabled.

The TXT instructions survive refreshes. Opening **Show DNS TXT record** reuses an active challenge. **Replace TXT record** requires an explicit inline action and invalidates the previous value. New challenges retain their public DNS value alongside its hash; existing hash-only challenges remain valid and are shown as unavailable for redisplay. An admin who already published a legacy value can check it. An admin who needs another value can explicitly replace it. The additive migration leaves historical proof unchanged.

Admin-scoped `GET /api/workspaces/{id}/domain-challenge` reads the current instructions without issuing proof. `POST .../domain-challenge/ensure` reuses active proof or issues it when absent/expired. The original POST explicitly replaces it. Concurrent ensure requests serialize on the workspace, and DNS verification rechecks proof, expiry, domain and administrator/key authorization after DNS collection and lock acquisition.

Workspace-scoped key sessions cannot add unrelated customers through `/api/customers`, whether using Bearer or token-login cookies. Their dashboard omits account-level customer creation and workspace switching. An admin can deny a pending membership even while active controls are paused; approval remains gated. Granting or revoking a temporary approval preserves scans when another current authorization still applies. Expiry notices direct users to current Workspace access.

## Customer creation review — October 9 implementation checkpoint

The dashboard keeps the currently displayed workspace selected while adding a customer. Each domain has an individual outcome: added, already has a workspace, or invalid. A new workspace shows its recorded creation time and ownership-review deadline. **Open workspace** explicitly selects its Overview, where TXT instructions and current access are available. An existing domain already approved for the account can be opened; otherwise **Request access** fills the separate request form without submitting it or granting access.

Creation has a pending-submit guard, a 20-second deadline covering transport/body reads, and account/result validation. Partial success, an unconfirmed response, and edits made while a request was pending retain the entered details. A complete confirmed success resets only the unchanged draft. Creation feedback is separate from access-request feedback. Its confirmed result survives an independent workspace-list read failure. Opening pauses until that account's saved access can be confirmed; **Refresh workspaces** retries only the read. A lost response directs the user to inspect saved workspaces before submitting again. There is no automatic write retry. Prior result rows remain dated and labeled with their own customer until another creation is confirmed; form drafts and that response view are not persisted across page navigation.

The API adds account identity, an observation date, created-workspace dates and `Cache-Control: no-store`. The dashboard submits `select_created_workspace: false`; the API default retains its existing selection behavior for other clients. Existing domains grant no new membership or onboarding approval and do not replace their verification records.
